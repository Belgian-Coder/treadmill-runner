# Customizing the Harness

Customize the canonical owner, then run its generator and checks. Do not customize generated adapters directly: the next sync will replace them.

## What To Change Where

| You want to change | Canonical files | Generated or derived files; do not hand-edit | Validate afterward |
|---|---|---|---|
| Repository-wide agent policy | `AGENTS.md` | `.github/copilot-instructions.md`, `.claude/CLAUDE.md`, `GEMINI.md`, `.continue/rules/repository-instructions.md`, `.aider.conf.yml` | `sync-instructions --check`, then `sync` after an intentional source edit |
| Human-tunable limits, warning actions, command budgets, and portable cost/context choices | Complete `.agents/project-policy.json` through `policy list`, `policy explain`, `policy set`, `policy reset`, and `policy refresh` | Effective policy reports and command measurements | `policy validate`, then the affected focused check |
| A reusable skill's trigger or behavior | `.agents/skills/<name>/SKILL.md`, `.agents/skills/<name>/module.json`, and owner-local `scripts/`, `docs/`, `assets/`, or `suites/` | `.agents/routing.md`, tool-only `.agents/registry.json`, `.claude/skills/<name>/SKILL.md` | owner self-tests/evals, `validate_skill.py`, `check-additions`, `sync`, `validate-agent-compatibility` |
| A workflow's phases, gates, tasks, or evidence | `automations/<name>/WORKFLOW.md`, `module.json`, optional `instructions.md`, `scripts/`, `templates/`, and `suites/` | `automations/routing.md`, tool-only `automations/registry.json`, generated schemas or maps declared by the owner | `validate-automations`, workflow eval/scorecard/smoke, `check-additions`, `sync` |
| Semantic worker profiles or host/model routing | `.agents/skills/workflow-manager/scripts/workflow_support/worker_profiles.json` and a workflow's `module.json.worker_profiles` | Context and handoff packets produced by lifecycle commands | workflow-manager self-tests, worker-profile checks, workflow context checks |
| Simple-task stopping rules | canonical semantics in `AGENTS.md`; route metadata in `.agents/skills/workflow-manager/scripts/workflow_support/worker_profiles.json` | generated host instruction adapters and lifecycle packets | workflow-manager self-tests, `sync`, `validate-agent-compatibility` |
| Installed CLI capability detection | `.agents/skills/skill-manager/scripts/validate_agent_compatibility.py`, its public CLI registration, tests, and eval suite | `docs/reference/commands.md` | focused skill-manager tests, `validate-agent-compatibility`, `commands --format markdown --write docs/reference/commands.md` |
| Provider usage, caching, or reasoning evidence | `.agents/skills/agent-benchmarking/scripts/support/`, provider adapter scripts, benchmark suites, and fixtures | Run receipts and trusted local captures | agent-benchmarking self-tests and the relevant comparison or matrix suite |
| Execution-harness experiments or trace metrics | `automations/agent-benchmarking/suites/execution-harness-experiments-v1.json` and `.agents/skills/agent-benchmarking/scripts/` | planned cells, result packets, and comparison reports | agent-benchmarking self-tests and the offline experiment planner |
| Optional local-AI policy, model, or hardware behavior | tracked `.agents/local-ai.json`, `.agents/local-ai/policy.json`, and `.agents/skills/local-ai-helper/`; machine choices in gitignored `.agents/local-ai/local.settings.json` | gitignored secrets, cache, models, runtimes, and downloads under `.agents/local-ai/` | `local-ai readiness`, `local-ai policy`, `local-ai doctor --quick`, helper tests, `sync --check` |
| Project-specific facts | `docs/project/project-context.md` through `project-context-review` and `project-context-apply-review` | Review JSON/evidence generated by those commands | project-context review, `setup --check`, `status --fast` |
| Human documentation | the owning `docs/**/*.md` file with required frontmatter | `docs/reference/commands.md` is generator-owned | link from `docs/start-here.md` or `documentation-map.md`, then `check-repo-health` |

The portability, provider-evidence, and customization extensions covered here are V1-only. When one of these contracts replaces an old form, update its canonical source, fixtures, tests, and docs together, remove obsolete files and fields, and keep that extension at `schema_version: 1`. Do not add translation layers, deprecated aliases, or parallel V2 files. Established contracts outside this change, such as the canonical module manifest contract, keep their owning version until they are deliberately replaced as a separate breaking change.

For a complete catalog of configurable limits and warning actions, use `python -B .agents/manage.py policy show` and read [Project Policy Configuration](../harness/policy-configuration.md). Safety-critical path, archive, credential, and resource-protection boundaries are intentionally not configurable.

## Example: Add A Repository Rule

Suppose every host must report skipped validation with a reason.

1. Add one concise rule to `AGENTS.md`.
2. Run the source-to-adapter generator.
3. Verify that every instruction adapter matches the source.

```shell
python -B .agents/manage.py sync-instructions
python -B .agents/manage.py sync-instructions --check
```

Do not repeat the rule manually in `.github/copilot-instructions.md` or `.claude/CLAUDE.md`. Those files are generated from `AGENTS.md` so Codex, Copilot, Claude Code, and the other supported instruction surfaces receive the same repository policy.

## Example: Customize A Skill

Suppose `repo-navigation` should recognize a new request phrase and produce one additional deterministic map.

1. Change its trigger and user-facing workflow in `.agents/skills/repo-navigation/SKILL.md`.
2. Put reusable behavior in that skill's `scripts/` directory and declare the output in `module.json` when the contract requires it.
3. Add focused self-test and eval coverage beside the owner.
4. Regenerate routing and Claude skill wrappers.

```shell
python -B .agents/skills/skill-manager/scripts/validate_skill.py .agents/skills/repo-navigation
python -B .agents/manage.py check-additions
python -B .agents/manage.py sync
python -B .agents/manage.py validate-agent-compatibility
```

Do not edit `.agents/routing.md`, the tool-only `.agents/registry.json`, or `.claude/skills/repo-navigation/SKILL.md`, and do not load the raw registry for agent context. Use `.agents/routing.md` or the compact routing commands instead. Copilot uses the canonical project skill; Claude Code receives a generated frontmatter-first wrapper that points back to it.

## Example: Customize A Workflow

Suppose a deployment workflow needs a separate security-review phase.

1. Update `automations/<workflow>/module.json` with the phase, task, gate, worker profile, inputs, outputs, and validation command.
2. Update `WORKFLOW.md` and `instructions.md` with the human and agent flow.
3. Add or update workflow eval cases and diagrams.
4. Validate the owner and regenerate routing.

```shell
python -B .agents/manage.py validate-automations --name <workflow> --strict-phase-quality
python -B .agents/manage.py eval-workflow --name <workflow> --suite automations/<workflow>/suites/workflow-evals.json
python -B .agents/manage.py workflow scorecard --name <workflow> --format json
python -B .agents/manage.py sync-automation-routing
```

Keep reusable security analysis in a skill and reference it from `module.json`; do not copy the skill's full behavior into the workflow.

## Example: Tune The Simple-Task Governor

Suppose a repository wants its low-risk documentation edits to stay serial, but permits escalation after a verifier failure.

1. Keep the portable behavior in one concise `AGENTS.md` rule: one worker, one scoped pass, one owning verifier, then stop unless failure or new evidence changes scope.
2. Change task classification or advisory host routes in `worker_profiles.json`. Keep the semantic `implementation-low` contract valid even when a preferred model or deliberation control is unavailable.
3. Add workflow-manager regression coverage for every new route, capability, and fallback.
4. Regenerate host adapters and validate discovery.

```shell
python -B .agents/skills/workflow-manager/scripts/run_self_tests.py
python -B .agents/manage.py sync
python -B .agents/manage.py validate-agent-compatibility
```

Do not require Codex TOML, Copilot personal settings, or Claude settings for repository correctness. Host-specific tuning is optional: an unattested route must fall back to the active model, stay serial, and preserve the same validation and stopping rule.

## Example: Extend An Execution-Harness Experiment

Suppose you want to compare a new guided-continuation strategy without enabling it in production.

1. First implement and validate the required host evidence adapter capabilities.
2. Add the experiment/arm to both the canonical contract in `execution_harness_experiments.py` and `execution-harness-experiments-v1.json`, with exactly three repetitions, isolated workspaces, deterministic checks, and explicit evidence requirements.
3. Do not add an arm that produces unexecutable cells. Never infer model identity, context inheritance, editor events, or provider usage from labels.
4. Run the offline planner. It validates and plans cells; it does not launch agents, call models, write targets, or promote results.

```shell
python -B .agents/skills/agent-benchmarking/scripts/execution_harness_experiments.py --suite automations/agent-benchmarking/suites/execution-harness-experiments-v1.json --format json
python -B .agents/skills/agent-benchmarking/scripts/run_self_tests.py --match execution_harness_experiments
```

The anchored-edit prototype remains dry-run-only and is not part of the canonical suite. Customize its benchmark assertions and fixtures under `agent-benchmarking`; use Codex, Copilot, or Claude Code's native editor for real files. Do not restore its comparison arm until host editor-event evidence is implemented, and do not add a portable write mode unless a later implementation can prove its file-installation race boundary and passes a new security review.

## Example: Add A Host Alternative

Suppose a future Copilot CLI exposes a static session capability under a new help flag.

1. Add the advertised-capability pattern to `HOST_PROBE_SPECS` in `validate_agent_compatibility.py`.
2. Keep the probe on a fixed argument allowlist. Version/help and Copilot's JSON skill listing are model-free; prompt, auth, update, doctor, MCP mutation, and interactive commands remain forbidden.
3. Add injected-runner tests for the exact argument vector, success, timeout, access denial, malformed output, and a zero-exit Copilot parser error on stderr.
4. Update the compatibility docs and eval help assertion.

```shell
python -B .agents/manage.py validate-agent-compatibility
python -B .agents/manage.py validate-agent-compatibility --installed-hosts --summary --compact --format json
python -B .agents/manage.py commands --format markdown --write docs/reference/commands.md
```

An advertised flag is an observation, not proof that a model-backed task works. If a host lacks an exact feature, use the portable alternative: direct tools, serial execution, durable workflow checkpoints, and generic prompt delivery.

## Example: Add A Provider-Specific Optimization

Keep provider-neutral behavior correct first. Then isolate the optimization in an evidence adapter.

- Stable prompt prefixes, opaque reasoning continuation handles, and hosted programmatic orchestration belong to the direct OpenAI Responses adapter.
- Claude API cache accounting belongs to a Claude provider adapter; it is not automatically a Claude Code capability.
- Copilot CLI usage facts come from its supported host evidence surface; never infer the provider from a model-like label.
- Codex, Copilot, and Claude Code all fall back to the same semantic profile and deterministic validation when a provider-specific fact is absent.

Add a provider adapter under `.agents/skills/agent-benchmarking/scripts/support/`, bind it to a V1 evidence contract, and add negative tests that fail closed for stale identity, incomplete usage, missing cache facts, or mismatched run scope. Never make provider-specific evidence mandatory for the generic path.

## Example: Customize Optional Local AI

Use local AI only as an optional evidence helper; deterministic checks and the active coding host remain authoritative.

1. Change shared, reviewable policy or model-bundle declarations in `.agents/local-ai.json`, `.agents/local-ai/policy.json`, or the owning `local-ai-helper` skill.
2. Put machine-specific GPU selection in gitignored `.agents/local-ai/local.settings.json`. Keep secrets in gitignored `.agents/local-ai/secrets.local.json` and caches, models, runtimes, and downloads out of Git.
3. After local profile/cache inspection is acceptable, run the normal read-only diagnostics below. These are not part of strict no-profile/no-cache validation.
4. Run bootstrap, downloads, model execution, or benchmarks only when the user and policy explicitly allow their writes, network access, and compute cost.

```shell
python -B .agents/manage.py local-ai readiness --summary --compact --json
python -B .agents/manage.py local-ai policy --summary --compact --json
python -B .agents/manage.py local-ai doctor --quick --summary --compact --json
python -B .agents/manage.py sync --check
```

Do not copy a personal runtime path, GPU choice, access token, downloaded model, or cache into tracked configuration. If local AI is unavailable, keep the deterministic fallback and report the optional capability as skipped or blocked.

## Finish Every Customization

Use the smallest owner checks while editing, then run the single authoritative repository gate:

```shell
python -B .agents/manage.py sync
python -B .agents/manage.py finish --summary --compact --format json
```

Use `finish --deep` for impact-selected integration checks and `finish --release-full` for exhaustive release validation. The latter includes the broad repository gate, workflow evals, isolated install smoke, and benchmark diagnostics.

Run write-mode `python -B .agents/manage.py format-json` only after intentional tracked JSON edits.

Use `validate-agent-compatibility --installed-hosts` only when local CLI observations are useful. It is opt-in so normal validation stays deterministic and installation-independent. Provider/model calls belong in explicitly approved benchmark runs, not in repository sync or compatibility checks.
